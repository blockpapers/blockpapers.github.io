Git 代理配置与推送记录

2026-06-25

问题缘起

这次是在给博客推送到 GitHub 的时候，先遇到了旧代理配置残留，后面又碰到远端连接不稳定。最后的处理方式很简单：先清掉旧代理，再统一改成 127.0.0.1:7890，然后重新推送。

先清掉旧代理

如果之前配置过 Git 代理，建议先看一眼当前状态：

git config --global --get-regexp '^(http|https)\.'

我这次是直接把全局代理清掉，再重设一遍，避免旧值干扰：

git config --global --unset-all http.proxy
git config --global --unset-all https.proxy

配置新代理

接着把 Git 的 HTTP 和 HTTPS 代理都指向本地代理服务：

git config --global http.proxy http://127.0.0.1:7890
git config --global https.proxy http://127.0.0.1:7890

确认一下结果也很直观：

git config --global --get-regexp '^(http|https)\.proxy$'

验证与推送

代理配置完后，直接推送当前分支到 GitHub：

git push -u origin main

如果你这边网络偶尔会抖，可以补一个强制 HTTP/1.1 的写法，通常更稳一点：

git -c http.version=HTTP/1.1 push -u origin main

这次最终是成功推上去了，仓库地址是 blockpapers/blockpapers.github.io.git。

小结

这类问题本质上就是两件事：先确认 Git 自己有没有残留代理，再确认本机代理服务是不是可用。把这两层理顺，后面的推送通常就顺了。

我现在会把这组命令当作固定排障套路：清旧代理、设新代理、验证、推送。简单，但很管用。
